# 余额单位 1:10 → 1:1 生产切换

本操作必须在余额充值关闭且 PostgreSQL 完整备份验证通过后执行。应用保持在线；迁移 SQL 先在线更新历史记录，最后使用短数据库锁排空扣费写入。迁移不放入应用启动流程，避免实例启动时自动修改资金数据。

## 口径

- 普通用户的充值资产、余额及所有客户计费字段按 `÷10` 折算。
- `s928215036@gmail.com` 仅充值形成的余额资产和余额订单按历史 `÷5` 折算。
- 该特殊用户的使用费率、API Key/平台用量与全站一样按 `÷10` 折算。
- 通道实付、手续费、订阅售价、原始上游成本、账号成本与相对倍率不变。

## 顺序

1. 导出迁移前行数、金额汇总和代表用户快照。
2. 设置 `BALANCE_PAYMENT_DISABLED=true`，确认无进行中支付、退款和批量任务。
3. 备份 PostgreSQL、`.env`、Compose、Nginx 和当前应用产物并验证备份可读。
4. 在独立端口启动同版本候选实例并验证健康，旧实例继续承载流量。
5. 用 `psql -X -v ON_ERROR_STOP=1 -f normalize-balance-denomination-1-to-1.sql` 执行单事务迁移；长历史更新不锁用户，最后短锁排空扣费并补齐并发新增日志。
6. 重启候选实例以清空进程内缓存，删除 Redis 中 `billing:*`、`apikey:auth:*` 等计费/鉴权缓存，不执行 `FLUSHALL`。
7. Nginx 切到健康候选实例后停止旧实例，执行 `reconcile-balance-denomination-tail.sql` 修正旧实例在途请求并退款多扣余额。
8. 验证持续新请求全部使用新倍率，并验证新充值订单的本金 `P` 对应到账 `P` 后恢复余额充值。
9. 创建 `active + popup + 全体用户` 公告并验证用户侧可见。

## 回滚

事务提交前失败会自动完整回滚。事务提交后不得用旧备份覆盖新写入，也不得把线上数值直接乘 `10`；应依据迁移 marker 的高水位执行尾账前向修正。只有在明确冻结流量并接受备份时间点之后的数据丢失时，才执行完整灾难恢复。
