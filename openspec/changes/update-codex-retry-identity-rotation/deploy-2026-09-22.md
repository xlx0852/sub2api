# 蓝绿上线记录（2026-09-22）

## 方式

蓝绿：新建候选容器跑新二进制（绿灯），nginx `upstream` 从旧容器（蓝灯）切到新容器，`nginx -s reload` 优雅切换。

- 绿灯容器复用蓝灯的镜像、挂载、116 条 env（env 经临时 600 权限文件注入，用后即删，不落库不打印）
- 唯一差异：`/app/sub2api` 绑定挂载指向新 release 目录
- 旧容器**保持运行**作为秒级回滚（改回 nginx 上游即可，无需重建容器）
- nginx 配置已备份（同目录 `.bak-overloadepoch-*`）

## 开关状态

- `DISABLE_CODEX_OVERLOAD_IDENTITY_ROTATION` 未设置 → 全局默认**开启**
- `OPENAI_CODEX_TURN_STATE_REUSE` 未设置 → 默认 **true**
- 账号级覆盖 `extra.codex_overload_identity_rotation` 未设置 → 跟随全局

## 当前实际生效范围（重要）

| 改动 | 是否生效 | 说明 |
|---|---|---|
| 过载即时清票 | ✅ | 与指纹模式无关；`turn_state` 复用默认开启 |
| 不可重放时清票 + 记爆发窗口 | ✅ | 同上 |
| 爆发窗口重试预算 +2 | ✅ | 同上 |
| **`thread-id` 轮换（含跨请求 epoch）** | ❌ **未生效** | 5 个活跃账号均为 `device` 指纹模式，该模式不改写 `thread-id` |

轮换要生效，必须先把灰度账号切到 `session`（或 `full`）指纹模式。`session` 是
`add-codex-fingerprint-convergence` 中「新建 OAuth 账号的默认值」，属于受支持的目标配置；
但切模式本身会改变上游可见指纹（N 会话 → 1 会话 + N 线程），因此 A/B 的两组必须**都切**，
只用账号级开关 `codex_overload_identity_rotation=on/off` 区分，否则两个变量无法归因。

## 观察点

上线后按 `rollout.md` 观察；因为 `server_is_overloaded` 出现频率低（本地全期 0.94%），
功能正确性优先于效果指标：

1. 是否出现 `[CodexTurnStateSeed] invalidate ... reason=server_overloaded ... session_epoch=N`
   —— 出现即证明「首次过载即清票」生效（旧行为需连续 3 次 5xx 才清）。
2. 同账号重试日志里 `overload_path` 是否出现（`http_503` / `stream_failed`）
   —— 这是首次能量化两条通道真实占比的数据。
3. 在账号切到 `session` 之前，不应出现 `thread_id_rotated=true`；若出现需排查。

## 分阶段激活（账号级）

生产 OAuth 流量高度集中：24h 内 5 个活跃 OAuth 账号里只有 1 个有量（其余 <78 请求），
而 OpenAI API-key 账号占比更高。**并发双臂 A/B 不成立**，因此改为同一账号内的分阶段激活：
指纹模式先切、轮换开关后开，这样任何上游异常都能归因到单一步骤。

| 步骤 | 时间 | 改动 | 结果 |
|---|---|---|---|
| 1 | 02:26 +0800 | 灰度账号 `codex_fingerprint_mode` `device`→`session`，`codex_overload_identity_rotation=off` | 无报错；无流量可验证 |
| 2 | 02:47 +0800 | 灰度账号 `codex_overload_identity_rotation` `off`→`on` | 配置就位，等待流量 |

- `extra` 键数 45 → 46（只新增 1 个键），`device`→`session` 为覆盖写入，**无字段丢失**（改动前已备份至 `/root/`，600 权限）
- 配置传播依赖调度快照全量重建（`GATEWAY_SCHEDULING_FULL_REBUILD_INTERVAL_SECONDS=300`）；
  `accounts` 表**无触发器**、`scheduler_outbox` 由应用写入，因此原生 SQL 改动不经 outbox，
  最迟 300s 后生效（旧笔记里的 `sched:acc:<id>` 键在当前版本已不存在，无需删除）

### 回滚（单账号）

```sql
-- 恢复为 device + 不覆盖开关（即完全退回旧行为）
UPDATE accounts SET extra = jsonb_set(
  jsonb_set(extra, '{codex_fingerprint_mode}', '"device"'::jsonb, true),
  '{codex_overload_identity_rotation}', '"off"'::jsonb, true)
WHERE id = <canary_id>;
```
等 ≤300s 生效。备份 JSON 在 `/root/acct69-extra-backup-*.json`，可整列还原。

### 1. 功能正确性（先看这个）

```bash
# 模式改写是否引入上游错误（session 模式会改写头 + client_metadata，出 bug 会表现为上游 4xx）
docker logs --since 30m <green> | grep -E '"account_id":<canary>' | grep -E 'ERROR|WARN|forward_failed'
```

### 2. 轮换是否触发

```bash
# 出现即证明「首次过载即清票」生效（旧行为需连续 3 次 5xx）
docker logs --since 2h <green> | grep 'reason=server_overloaded'
# 首次拿到两条通道的真实占比
docker logs --since 2h <green> | grep -oE 'overload_path=(http_503|stream_failed)' | sort | uniq -c
# 轮换是否真正作用于派生（session 模式下才应出现）
docker logs --since 2h <green> | grep -c 'thread_id_rotated=true'
```

### 3. 代价指标：prompt cache 命中率

`session` 模式把 `session-id` 从「每客户端」改为「账号级常量」，会改变上游缓存命名空间，
命中率短期下降属预期。口径 `cache_read/(input+cache_read)`（`input_tokens` 只记非缓存部分，
直接相除会得到 >100% 的假值）：

| 对象 | 改动前基线 |
|---|---|
| 灰度账号 69（近 5 天汇总） | **90.01%**（日 86.5–92.7%） |
| 对照账号 89（apikey，不受影响） | **87.71%** |

流量回来后对比灰度账号的命中率与对照账号，确认下降幅度与「发生过过载的会话占比」量级一致，
而不是全量下降（全量下降说明轮换扩散到了未过载会话）。
