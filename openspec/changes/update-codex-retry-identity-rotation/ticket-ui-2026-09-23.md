# 二十一、账号详情页的打票可视化（2026-09-23）

## 21.1 做了什么

账号详情抽屉（`AccountUsageDrawer`，账号唯一的"详情"界面）新增**打票**页签，
展示 `codex_ticket` 摘要：

| 区 | 内容 |
|---|---|
| 供应池票位 | 每个池：池名、**形态**（票长，292 高亮）、可回放/已过期、落点模型、票龄进度条（相对 60 分钟回放窗口） |
| 会话 Cookie | 有效数量、最近刷新时间、**出口指纹**、可用/已过期 |

页面文案明确写了：**形态与池的对应只在"同账号同期"成立**（astra↔292、luna/sol/terra↔312），
跨账号不成立（实测账号 69 多个池都是 292，132/133 是 332/356）——避免这个可视化反过来
强化社区那个错误的"292 = 目标池"前提。

## 21.2 顺带修掉一个真实泄露面（本次最重要的改动）

`AccountFromServiceShallow` 此前是 `Extra: a.Extra` **原样下发**。而 extra 里现在既有
`openai_codex_turn_state*`（上游签发的**会话令牌**）也有
`openai_codex_turn_state_cookies`（**会话 cookie 值**）——都会进浏览器。

本仓对 credentials 的既有约定是不下发前端、只给存在性（`dto.RedactCredentials`），
票与 cookie 同属会话凭据，必须遵守同一条：

- `service.RedactCodexTicketExtra`：剥离票与 cookie 键，**保留其它 extra 键**（前端大量设置项从这里读），
  且**不改入参**（调度器还在用同一个 map）。
- `service.BuildCodexTicketSummary`：只给派生信息（形态/票龄/是否可回放/池位/cookie 数量/出口指纹）。
  逻辑放 service 而非 dto，因为回放窗口、cookie 新鲜期、池槽位键名与单值兜底的口径都在该包内，
  复制到别处迟早与真实行为漂移。

## 21.5 上线后首个反馈：页签里没有数据 → 根因与修复

**部署侧先排除**（全部核对过）：nginx 指向 `ticketui-f3a820898`；容器内
`/app/sub2api` 的 sha256 与发行文件一致；`strings` 命中 `codex_ticket`；
库内确实有账号带池票与 cookies。

**根因在前端的行合并策略**（`AccountsView.vue`）：

```ts
if (shouldReplaceAutoRefreshRow(currentRow, nextRow)) { ...; return nextRow }
return currentRow        // 未"变化"的行直接沿用内存里的旧对象
```

而 `shouldReplaceAutoRefreshRow` 只比较 `updated_at / status / schedulable /
current_concurrency / rate_limit_reset_at / overload_until / temp_unschedulable_until /
OpenAI 用量键`——**与票完全无关**。于是：

1. 在**后端部署之前**打开过账号页的会话，内存里的行没有 `codex_ticket`，
   自动刷新又一直保留旧对象 ⇒ 打票面板**永远是空**。
2. 即便重新加载过，页签开着时**采票状态变化也不会传播**（每次采票、每次过载失效都会改）。

**修复**：面板改为**打开页签时按 id 取一次账号详情**（`GET /admin/accounts/:id`，
该接口走 ent 全字段、带 `extra`），不再依赖列表行；列表行里若已有摘要则作为兜底。
另加两条：切换账号时重取（避免把 A 的票显示给 B）、详情失败显示提示而不是空面板。

**教训**（比这个 bug 本身更值得记）：本仓的列表行有"未变化就沿用旧对象"的优化，
**任何"新字段/派生状态"都不能假设它会随自动刷新到达前端**。
