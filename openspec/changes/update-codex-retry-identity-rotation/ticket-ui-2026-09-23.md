# 二十一、账号详情页的打票可视化（2026-09-23）

## 21.1 做了什么

账号详情抽屉（`AccountUsageDrawer`，账号唯一的"详情"界面）新增**打票**页签，
展示 `codex_ticket` 摘要：

| 区 | 内容 |
|---|---|
| 供应池票位 | 每个池：池名、**形态**（票长，292 高亮）、可回放/已过期、落点模型、票龄进度条（相对 60 分钟回放窗口） |
| 会话 Cookie | 有效数量、最近刷新时间、**出口指纹**、可用/已过期 |

页面文案明确写了：**形态与池的对应只在"同账号同期"成立**（astra↔292、luna/sol/terra↔312），
跨账号不成立（实测账号 69 多个池都是 292，132/133 是 332/356）——避免这个可视化反过来
强化社区那个错误的"292 = 目标池"前提。

## 21.2 顺带修掉一个真实泄露面（本次最重要的改动）

`AccountFromServiceShallow` 此前是 `Extra: a.Extra` **原样下发**。而 extra 里现在既有
`openai_codex_turn_state*`（上游签发的**会话令牌**）也有
`openai_codex_turn_state_cookies`（**会话 cookie 值**）——都会进浏览器。

本仓对 credentials 的既有约定是不下发前端、只给存在性（`dto.RedactCredentials`），
票与 cookie 同属会话凭据，必须遵守同一条：

- `service.RedactCodexTicketExtra`：剥离票与 cookie 键，**保留其它 extra 键**（前端大量设置项从这里读），
  且**不改入参**（调度器还在用同一个 map）。
- `service.BuildCodexTicketSummary`：只给派生信息（形态/票龄/是否可回放/池位/cookie 数量/出口指纹）。
  逻辑放 service 而非 dto，因为回放窗口、cookie 新鲜期、池槽位键名与单值兜底的口径都在该包内，
  复制到别处迟早与真实行为漂移。

## 21.3 验证

| 断言 | 位置 |
|---|---|
| 形态 = 票长；10 分钟票在窗口内、90 分钟票已过期；池票优先、单值兜底不重复；非 OAuth 返回 nil | `service` 单测 |
| **序列化后的摘要字节里不含票/cookie 值、不含 `gAAAAA`** | `service` 单测（断言的是字节，那才是真正离开进程的东西） |
| 剥离只删票/cookie 键，其它键保留，且不改入参 | `service` 单测 |
| **账号 DTO 出线字节**：无票、无 cookie 值，`codex_ticket` 带形态，其它 extra 键仍在 | `dto` 单测 |
| 面板渲染池位/形态/新鲜度/落点模型/cookie 数量/指纹；**extra 里的票与 cookie 值不入 DOM**；无摘要时空状态 | 前端 4 个用例 |
| 抽屉页签枚举与切换（新增第 5 个页签） | 前端用例（并改为**按 key 定位页签**，不再按索引） |
