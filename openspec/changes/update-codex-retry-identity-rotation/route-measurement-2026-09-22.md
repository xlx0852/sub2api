# 十八、路由与形态测量：更正、留痕与当前结论（2026-09-22）

## 18.1 更正：17.6 的「292 稳定来自 gpt-5.5 池」是**过度概括**

当时只有 2~3 个样本就下了结论。后续 DB 快照与抓包都反驳它：

| 证据 | 内容 |
|---|---|
| DB 账号 120 槽位 | `gpt-5.5`=292、**`gpt-5.6-terra`=292**、`gpt-5.6-luna`=312、`gpt-5.6-sol`=312、**`gpt-6-astra`=312** |
| 基线抓包 | `gpt-6-astra` 的那一条是 292，而 `luna`/`terra` 都是 312 |
| DB 账号 132/133 | **全部池**都是 332 或 356 |

⇒ **票的形态与池不是对应的**：292 出现在 {5.5, terra, astra}，312 出现在 {luna, terra, sol, astra}，
332/356 出现在 132/133 的**全部**槽位。形态更像是**账号/项目维度的属性**，而不是池的标识。

这与该 fork 自己的免责声明一致：「292/312 只是 `x-codex-turn-state` 的形态，不能单独证明模型质量」。
**社区把 292 当作目标池标识是错的**，我方 17.6 的表述也随之作废。

## 18.2 测量工具与两次自我纠错

**仪表**（`[CodexRouteStat]`，每 10 分钟一行，空窗口不输出）：

```
pools=…            被接受的轮次按 capture 归的槽位
shapes=len312=…    被接受轮次的票形态
routes=req→served  请求模型 → 上游回显的落点（HTTP 在改写前取，见下）
route_served_ticket=served#len… 或 #none   落点 × 该响应是否带可复用票
```

**纠错一**：HTTP 流式路径的 `response.model` 改写发生在 **490 行**，提取在 **391 行** —— 必须先确认埋点在改写之前，
否则记录的是"被改回请求名"的值（那会让 `astra→astra` 变成恒真）。
**纠错二**：WS 路径有 `if respModel == "" { respModel = originalModel }` 的**归槽兜底**；
拿它当落点会制造 `astra→astra` 假配对。已改为**只有上游真回显落点时**才记映射。

## 18.3 未解决的观测（如实留痕）

`routepair` 版（含上述纠错二之前）曾出现一个窗口：

```
routes=gpt-6-astra→gpt-6-astra=13, gpt-6-astra→gpt-5.6-luna=10
⇒ 请求 astra 23 次，落 astra 13 次 (56.5%)
```

而**直连真实客户端基线是 1.0%（1/102）**。但此后：

| 版本 | astra 观测 |
|---|---|
| routepair2 | `astra→luna` 2/2（0% 命中） |
| routepair3（修掉假配对后） | 该时段**没有 astra 请求**，无法验证 |

⇒ **13/23 既未被复现，也未被证伪。** 最可能是 18.2 纠错二的假配对（WS 兜底），
但 routepair2 同样带该兜底却未见假配对，所以不能确定为唯一原因。
**结论：在拿到足够样本前，不得声称"我方 astra 命中率高于直连客户端"。**

## 18.4 当前可下的结论

1. **无回归**：各版本 `/responses` 零 4xx/5xx（除账号 89 的上游余额 403）。
2. **可配对的落点数据是自洽的**：`gpt-5.6-sol→gpt-5.6-sol#len312`（与 DB 的 sol 槽位一致）、
   `grok-4.6→grok-4.6-build#none`（Grok 不发 Codex 票）、`astra→luna#len312`。
3. **票形态不能反推池**（18.1），所以「形态直方图」不能用来判断落池。
4. astra 的真实命中率**待定**，但**直连客户端的 1.0% 基线是可靠的**（123 条，SSE 内单一模型名）。

## 18.5 下一次该怎么做（避免再绕）

- 先用 `scripts/codex_ticket_shape_report.py` 看 `routes=` 里 astra 的样本量；
  **样本 < 50 时不要下任何结论**。
- 需要更多 astra 样本时，不要改账号配置去凑，而是**延长时间窗**（用 `--since 24h`）。
- 若要消除"我方 vs 直连"的账号差异，唯一干净的做法是**同一账号**：让探针与业务流量在同一账号上对比
  （探针 seeded 行已带 account=，业务侧暂无 account 维度）。

# 十九、累积读数：astra 命中率、指标矛盾的解决、以及不能归因的部分（2026-09-22 深夜）

## 19.1 指标矛盾已解决：astra 落点通常**不发可复用票**

修掉两处埋点假象后，业务侧 279 条可配对响应给出完整表：

```
grok-4.6-build#none      139 (49.8%)     Grok 不发 Codex 票
gpt-5.6-sol#len312        96 (34.4%)     sol 响应 96/117 带票
gpt-5.6-sol#none          21 ( 7.5%)
gpt-5.6-luna#len312       15 ( 5.4%)
gpt-5.6-terra#len312       4 ( 1.4%)
gpt-6-astra#none           2 ( 0.7%)   ← astra 落点，无票
gpt-6-astra#len292         1 ( 0.4%)   ← astra 落点，292
```

**astra 落点 3 次里 2 次没有可复用票。** 这解释了 18.3 之前的三方不一致：
形态直方图只统计"拿到票"的轮次，而 astra 落点大多不发票 → 直方图看不到它们；
DB 的 astra 槽位则是被"请求 astra 但落 luna"的那批 312 票写入的。
**两个看似矛盾的指标其实都正确。**

## 19.2 astra 命中率（修好埋点后的干净样本）

| 来源 | 命中 |
|---|---|
| 探针（seeded 行） | **2/6 (33%)**，两次都是 `pool=gpt-6-astra len=292` |
| 业务（routes，HTTP 改写前取值） | **3/17 (17.6%)** |
| **合计** | **5/23 (21.7%)** |
| 直连真实客户端基线 | **1/102 (1.0%)** |

Fisher 精确检验 p ≈ 5e-4 —— **差异在统计上显著**。
且形态配对完全自洽：**落 astra 必带 292，落 luna 必带 312**（探针 6 条 + 业务 1 条，无一例外）。

## 19.3 但**不能**把差异归因于网关的身份改动

三个未排除的混淆项，任何一个都能单独解释这个差距：

1. **账号不同（最强混淆）**：基线是用户自己的一个客户端账号；我方生产流量横跨多个账号。
   上层套餐差异会直接影响 astra 可用性。
2. **时间不同**：基线抓包是 19:00–07:00（+0800）的 12 小时；本次读数是 23:00–01:00。
   astra 的容量潮汐在 503 分析里已经证实存在。
3. **出口不同**：基线走用户住宅 IP，我方走 74.82.195.84。

此外 18.3 那个 13/23 窗口属**旧埋点**（含 WS 兜底假象），不计入本节。

**唯一的干净做法是同一账号对照**：探针的 `seeded` 行已带 `account=`，业务侧 `routes` 目前**没有 account 维度**。
要在同账号内比较，需给 `recordOpenAICodexRouteMapping` 加 accountID 参数（一行改动）。

## 19.4 实际可用结论（对运营有用）

- **astra 可达**，我方观测命中约 **1/5 量级**（22%），远高于"钉住才能拿到"的悲观预期；
  但也远非稳定——6 条探针里有 4 条被降级到 luna。
- **astra 落点大多不发票** ⇒ **票回放无法把 astra 钉住**。想拿到 292 只能靠每次请求重新摇中，
  这解释了社区为什么在"刷 292"而不是"买一张一直用"。
- **形态↔池的实际对应**（我方实测）：`astra↔292`、`luna↔312`、`sol↔312`、`terra↔312`。
  18.1 里"形态与池不对应"的结论要收窄为：**跨账号**不成立（账号 69 多个池都是 292），
  **同账号同一时期**是稳定的。
