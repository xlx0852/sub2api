## Context
成功请求写入 usage logs，终态失败写入 ops error logs。一次外部请求可能经历上游重试并产生多条内部错误，因此不能简单把两张表的行数相加。首页需要表达用户实际看到的最终结果，而不是内部尝试次数。

## Goals / Non-Goals
- Goals: 用真实终态请求衡量用户体验；保证管理员与普通用户的数据权限边界；提供稳定的时间桶序列。
- Non-Goals: 不用该指标替代账单、SLA 或账号健康诊断；不删除现有主动监控功能。

## Decisions
- Decision: 以 request_id 为主要去重键，同一 request_id 存在成功使用记录时按成功计算；只有终态且未恢复的错误才计为失败。
- Decision: 缺少 request_id 的历史记录使用保守的独立样本计数，不尝试基于时间和模型猜测合并。
- Decision: 默认窗口为最近 24 小时，返回连续 144 个 10 分钟桶；空桶显式返回无请求状态。
- Decision: 平均响应仅取成功 usage logs 的 duration_ms，避免失败路径缺失或阶段性耗时扭曲结果。
- Decision: 用户接口强制按认证用户 ID 过滤；管理员接口允许全站聚合。

## Risks / Trade-offs
- ops error logs 与 usage logs 保留周期可能不同，较老窗口会出现口径差异；默认 24 小时可降低影响。
- 历史错误缺少 request_id 时无法精确去重；接口返回的样本数仍以可验证记录为准。
- 大流量实时聚合可能增加数据库负担；通过固定时间窗口、时间索引和短缓存控制开销。

## Migration Plan
无数据库结构迁移。先上线聚合接口与前端切换，保留主动监控页面作为独立诊断能力；回滚时首页恢复读取渠道监控接口。
