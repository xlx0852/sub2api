## Context

费用先由 token/请求/媒体价格与用户倍率计算，再分别流向余额、订阅、配额、缓存和用量日志。各目标列精度不同，且当前没有一个共享的规范金额，导致同一请求难以精确对账。

## Goals / Non-Goals

- Goals: 正费用统一六位上入；所有客户计费账本使用同一金额；保持跨版本幂等重试兼容。
- Non-Goals: 不修改模型价格、倍率、充值、退款、采购成本、历史数据或数据库列类型。

## Decisions

- Decision: 规范单位为 `10^-6 USD`，正费用使用十进制 `Ceil` 上入；例如 `0.000000001 -> 0.000001`，`0.123456001 -> 0.123457`，`0.123456000 -> 0.123456`。
  - Rationale: 满足正向费用不被抹零且避免 `float64 * 1e6` 在边界处误进位。
- Decision: 上入前先按现有 `usage_logs.actual_cost DECIMAL(20,10)` 的来源精度消除 `float64` 二进制尾差，再执行六位上入。
  - Rationale: 数学上精确的 `0.036` 在 Go 中可能表现为 `0.036000000000000004`，不能因此多进一个量化单位。
- Decision: 只规范最终客户费用及从该费用派生的配额消耗；输入、输出、缓存等价格明细保留原始计算精度。
  - Rationale: 明细用于解释价格构成，最终 `actual_cost` 才是应收事实。
- Decision: 请求指纹先使用原始金额生成，随后才生成六位规范金额。
  - Rationale: 部署前已开始、部署后重试的同一请求仍能命中原幂等身份。
- Decision: 客户应收规范金额必须回写到后续日志、余额、订阅、客户配额与缓存同步参数，禁止这些消费者再次独立舍入；账号成本配额保留其独立成本口径，但使用同一个六位上入函数。
  - Rationale: 仅在 SQL 命令中量化仍会让利润收入和缓存保留原始金额，无法完整对账。
- Decision: 退款、充值、人工调整和负向资金动作不复用该正向上入函数。
  - Rationale: 对负向资金使用“利于平台”的不对称舍入会改变退款合同，超出本次范围。

## Risks / Trade-offs

- 每个非零请求最多增加不足 `$0.000001` 的费用；通过页面说明、边界测试和上线前差额推演保持透明。
- 原始费用明细之和可能比最终 `actual_cost` 少不足 `$0.000001`；接口应将 `actual_cost` 明确视为最终应收。
- `harden-usage-billing-admission` 的预留/捕获若使用原始金额可能与最终上入金额差一个量化单位；实现时必须复用同一规范函数。

## Migration Plan

1. 先加入纯函数和边界测试。
2. 将共享网关与 OpenAI 专用路径的最终费用接入规范函数。
3. 验证余额、订阅、API Key、账号配额、缓存和用量日志精确一致。
4. 对近期线上用量做只读差额推演后部署；不回算历史账目。
5. 回滚时恢复旧二进制即可，新产生的六位费用仍是现有金额列的合法值。
