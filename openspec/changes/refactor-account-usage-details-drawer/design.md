## Context

`AccountUsageCell` 目前同时承担平台判断、额度加载、今日统计、错误状态、额度操作和全部行内展示。信息在 372px 单元格内纵向堆叠，平台数据越完整，行高和视觉复杂度越高。现有 `AccountStatsModal` 已能展示历史统计，但不能承载上游额度、连接性能和诊断状态。

## Goals / Non-Goals

- Goals:
  - 让账号列表适合快速扫描和横向比较
  - 在不丢失现有数据的前提下建立统一详情层级
  - 明确区分上游额度、本地消耗、性能和诊断信息
  - 复用现有 API、格式化和额度刷新逻辑
- Non-Goals:
  - 不修改后端用量聚合、计费或额度探测接口
  - 不统一不同上游本身不存在的额度维度
  - 不新增账号调度或自动禁用规则

## Decisions

### 1. 列表只保留可比较的摘要

摘要由三个稳定区域组成：账号风险状态、最多两个主要额度窗口、今日消耗。平台特有的套餐、错误详情、数据来源和重置能力进入抽屉。

当平台没有官方额度时，摘要显示本地今日请求、Token 和费用，不伪造额度进度。

### 2. 详情使用右侧抽屉

桌面端抽屉覆盖页面右侧并保留账号列表上下文；管理员可以直接点击其他账号切换详情。窄屏使用全宽详情层，避免表格与抽屉同时压缩。

### 3. 详情与统计按职责分层

- 额度：官方额度窗口、利用率、重置时间、套餐等级
- 性能：首 Token、平均/P90 总耗时、成功率和连接指标
- 诊断：数据来源、最后更新时间、响应状态、探测错误和重新授权提示

本地历史消耗、趋势和模型分布作为“统计”页签合并进同一个抽屉。操作菜单中的“查看统计”直接打开该页签，不再叠加第二个弹窗，也不在额度页重复展示统计摘要。

### 4. 操作文案使用固定语义

- `刷新额度`：主动请求上游官方额度
- `查看详情`：打开详情抽屉
- `查看统计`：打开详情抽屉中的统计页签
- `重新授权`：进入 OAuth 恢复流程

同一操作在不同平台不得使用“查询”“探测”“刷新”等多个名称。

### 5. 保留现有数据链路

抽屉只重组现有前端状态和接口结果。平台额度加载继续使用当前按需队列和缓存；列表不可因为打开抽屉而为所有账号新增高频上游请求。

## Risks / Trade-offs

- 抽屉同时展示多个数据源，必须明确更新时间和来源，避免把本地消耗误认为上游额度
- 将详情移出表格后，管理员需要一次点击才能看到完整数据；摘要必须保留风险状态和关键窗口
- `AccountUsageCell` 需要拆分数据适配与视图组件，否则只移动模板会继续积累平台分支

## Migration Plan

1. 提取统一的账号用量展示模型和平台适配器
2. 将现有行内展示替换为摘要组件
3. 新增详情抽屉并接入四个页签
4. 迁移现有统计弹窗能力，保留兼容入口
5. 完成桌面、窄屏、加载、空态和错误态验证
