# Design: Wire the Codex client version auto-sync runner into the application

## Context

`OpenAICodexVersionSyncService` periodically reads the latest stable `rust-v*` release of
`openai/codex` (primary path `GET /repos/openai/codex/releases/latest`, fallback: one 30-entry page
scanned for stable `rust-v` tags) and persists it to the setting
`openai_codex_client_version_synced`. `GetOpenAICodexClientVersion` resolves the effective value as
panel (`openai_codex_client_version`) → synced → compiled constant, and the gateway uses that value
for the outbound Codex identity and for the version-gated Codex models manifest.

The service was implemented, tested, and exported from the provider set, but never started in
production. Diagnosis:

| probe | result |
| --- | --- |
| `grep -c CodexVersionSync backend/cmd/server/wire_gen.go` (HEAD) | `0` |
| same file in deployed revision `2694ea76c` (v0.1.392) | `0` |
| `go run github.com/google/wire/cmd/wire check ./cmd/server` | no diagnostics |
| `wire diff ./cmd/server` (regenerated with wire v0.7.0) | 156/156 lines, variable renames only |
| `wire show ./cmd/server` | single injector `initializeApplication`; no version sync node |
| `settings.openai_codex_client_version_synced` | `0.153.4`, `updated_at` 2026-09-05 07:06:15+08 |
| `settings.openai_codex_version_auto_sync_enabled` | `true` |
| container logs matching `openai_codex_version_sync` | 0 lines |
| container egress `https://api.github.com/repos/openai/codex/releases/latest` | `200` |

Root cause: wire drops providers that no injector node consumes, and neither `ProviderSet`
membership nor `wire check` reports it. The feature is inert with no failure signal.

## Decisions

### D1: Fix by giving the runner a consumer, not by starting it somewhere else

Calling `Start()` from `main` would introduce a second, unenforced wiring path and would still leave
`wire_gen.go` disagreeing with the graph. The runner must be reachable from the injector:
`provideCleanup(...)` in `cmd/server/cleanup.go` takes it as a required parameter, so
`initializeApplication` cannot be generated without constructing it. This makes accidental omission a
compile failure instead of a silent no-op.

Accepted alternative (rejected): a separate background-service aggregator type. The codebase has 36
services in the `provideCleanup` list; introducing a second lifecycle surface for one service adds a
pattern without removing one. The `architecture-governance` requirement already asks background
services to register lifecycle hooks; `provideCleanup` is the existing registry façade for that.

### D2: Regenerate `wire_gen.go` instead of hand-adding the call

The file is marked `// Code generated by Wire. DO NOT EDIT.` but has been maintained partly by hand,
so its variable names no longer match wire v0.7.0's output. Regenerating is verified safe:

- `wire gen ./cmd/server` gives a 156-added/156-removed diff consisting only of local variable
  renames (`userRepository` → `v`, `secretEncryptor` → `v20`, …) — same call order, same arguments.
- `go build ./...` passes with the regenerated file.

Benefit: after this change `wire diff ./cmd/server` is empty, so any future drift (including another
unreachable provider) shows up as a reviewable diff. A hand-edit would leave the file permanently
out of sync with its own generator and hide the next omission the same way.

Two supporting details, both verified:

- The generator's CLI dependency (`github.com/google/subcommands`) is kept in `go.sum`. Without
  those two lines, *running* the generator mutates the tracked `go.sum`, so a regeneration would
  never be a clean, no-surprise diff.
- Because dropping the runner from `provideCleanup` (and regenerating) would compile fine, the
  generated injector is additionally asserted by a source-level test
  (`TestCodexVersionSyncIsWiredIntoGeneratedInjector`), so that regression fails the test step
  instead of silently stopping the sync again.

### D3: Every skip path logs its reason

Today only a successful advance (`openai_codex_version_synced`), a persistence failure, and fetch
failures log anything; "disabled", "already fresh", and "no newer version" are silent, which is why a
3.5-week freeze looked like normal operation. The runner will log, at `info`:

- `openai_codex_version_sync_started` with the interval on `Start()`,
- `openai_codex_version_sync_initial_skipped` with the age of the synced value when `runInitial`
  skips,
- `openai_codex_version_sync_noop` with `reason=disabled` | `reason=up_to_date` |
  `reason=not_advanced`.

Steady-state cost is ≤ 2 lines per 6 hours; the warning paths keep their current event names.

### D4: No GitHub token, no interval change

`ProvideGitHubReleaseClient` builds an unauthenticated client unless `UPDATE_GITHUB_TOKEN` is set.
Unauthenticated GitHub allows 60 requests/hour/IP; this runner needs 1 request per 6h (2 when the
`/releases/latest` path fails and the list fallback runs) plus at most one extra request per process
start when the synced value is stale (fresh values skip the initial sync). That is far inside the
budget, and the production container reaches `api.github.com` directly (no proxy configured). Adding
a token would add a secret to manage for no operational gain, so it stays out of scope and the limit
is recorded as a known limitation instead. 6h is likewise unchanged: upstream releases are daily at
best.

### D5: A frozen value is diagnosed from logs and `updated_at`, not from a new admin field

Exposing a "last sync attempt" timestamp would need a new setting, a DTO field, and frontend/i18n
work. The setting row's own `updated_at` plus the new reason-coded logs cover the failure modes seen
here without widening the API. Recorded as a known limitation; the admin gateway tab already shows the
synced value next to the panel field.

## Known limitations

- Unauthenticated GitHub API rate limit is 60 requests/hour/IP. If the host's egress IP is shared or
  throttled, sync degrades to the warn logs (`openai_codex_version_sync_*_fetch_failed`) while the
  stored value is retained; there is no alerting on repeated failures.
- Version freshness itself is not surfaced as a status/health signal; an operator must read the logs
  or the setting row's `updated_at`.
- The runner follows `openai/codex` stable releases only. A wrong or malicious `rust-v` tag inside
  that repository would be trusted as-is; the value is only used as an advertised client version
  string (normalized and compared numerically), never as a path or URL.

## Verification

- `go build ./...`, `gofmt -l`, and the touched packages' tests
  (`./internal/service/`, `./cmd/server/`).
- `go run github.com/google/wire/cmd/wire diff ./cmd/server` prints nothing (graph matches the file).
- `gotags`-free check that the file really compiles into the binary:
  `go build -o /tmp/sub2api ./cmd/server` then `go tool nm /tmp/sub2api | grep -i codexversionsync`.
- `openspec validate update-codex-client-version-sync --strict`.
- Post-deploy (operational, not part of the change): the setting row advances to the then-current
  stable version and a `openai_codex_version_synced` line appears in the container logs within the
  first startup window.
