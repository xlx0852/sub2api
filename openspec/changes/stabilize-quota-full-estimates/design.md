## Context

上游只提供额度窗口的 `used_percent` 和重置时间，不提供美元容量。本地界面把 usage log 按 API 标价折算为账号成本，再用当前累计成本除以当前百分比外推满额值。该算法把两个不同频率的信号直接相除，并且没有表达样本量或不确定性。

## Goals / Non-Goals

- Goals:
  - 让预估反映同一真实窗口内“新增本地消耗对应新增上游利用率”的关系
  - 避免低百分比和快照滞后产生数百美元的伪差异
  - 让管理员能区分可靠估算、低置信度外推和样本不足
  - 控制观测持久化与聚合成本，不放大真实上游探测频率
- Non-Goals:
  - 不把本地 API 标价成本描述成 OpenAI 承诺的美元额度
  - 不推断或修改模型厂商的真实配额策略
  - 不改变请求路由、账号暂停阈值或用户计费

## Decisions

### 1. 观测点与额度窗口绑定

每个观测点保存账号、平台、窗口类型、窗口起止、观测时间、上游 used%、累计请求、Token、账号成本和用户扣费。窗口重置后不得跨窗口计算斜率。

只有 used% 相对该窗口最近观测发生有效变化时才新增观测；重复探活或 UI 轮询不产生重复样本。

### 2. 优先采用增量斜率

当同一窗口至少存在两个有效观测点，且 used% 跨度达到 5 个百分点时：

```text
full_cost = (latest_cost - baseline_cost) * 100 / (latest_used - baseline_used)
```

基线选择当前窗口内能提供最大有效百分比跨度的较早观测。成本或利用率倒退、跨窗、时间逆序的样本不参与估算。

### 3. 明确降级和置信度

- 当前 used% 小于 5：不返回金额预估，状态为 `insufficient`
- 尚无有效增量跨度但 used% 不小于 5：允许使用累计线性外推，状态为 `low`
- 增量跨度 5～19 个百分点：`medium`
- 增量跨度不小于 20 个百分点：`high`

API 同时返回 `method`、`confidence`、`sample_count`、`used_percent_span` 和基于百分比量化误差形成的上下界。前端必须展示置信度，并把金额称为“API 标价等值预估”。

### 4. 将本地统计截止到观测时间

观测成本只聚合到上游快照的 `observed_at`，不得包含快照之后继续产生的请求。这样可以消除 used% 已冻结但成本仍增长造成的锯齿上冲。

### 5. 写入不进入请求关键路径

被动流量头触发的观测采用现有额度更新链路，并在 used% 未变化时快速返回。持久化失败不得影响上游响应；主动探活和真实流量共享同一幂等观测逻辑。

## Risks / Trade-offs

- 上线初期没有历史观测，部分账号暂时只显示低置信度或样本不足；这是避免伪精度的预期行为
- 工作负载结构在窗口内变化时，增量斜率仍可能变化；通过置信度和区间表达，而不是承诺固定容量
- 新增聚合查询会增加数据库工作量；只在 used% 变化时执行，并依赖 `usage_logs(account_id, created_at)` 与观测窗口索引

## Migration Plan

1. 新增观测表和索引，不回填无法与历史 used% 对齐的数据
2. 接入额度更新后的幂等观测写入
3. 后端优先读取增量估算，保留兼容字段和低置信度降级
4. 前端展示估算方法、置信度和区间
5. 验证查询耗时、写入频率和已有账号用量接口兼容性
