## Context

线上证据显示过载跨多个 OpenAI OAuth 账号同步发生。并发限制为 1 不能消除上游容量波动；短流的早期错误可以重试恢复，已经输出内容后的 `response.failed` 则不能安全重放。

## Goals / Non-Goals

- Goals: 降低用户可见 503；避免同一请求重复撞击同一账号；保护计费与流式内容一致性；保留可诊断性。
- Non-Goals: 不绕过 `codex_cli_only`；不修改共享账号健康语义；不在本变更中引入跨模型降级；不调整用户并发配额。

## Decisions

- Decision: 将可重试错误分为“未输出可见内容”和“已输出内容”两类；仅前者允许跨账号重放。
- Decision: 每个请求维护已尝试账号集合，账号选择从同组未尝试且可调度账号中挑选；若无其他账号，才按受限次数进行同账号重试。
- Decision: 对 `server_is_overloaded`、明确 503/502 的上游服务不可用错误使用短暂账号冷却；认证、余额、模型不存在等永久/业务错误不走该冷却策略。
- Decision: 冷却采用内存/现有调度状态的短 TTL，并通过结构化日志记录，不新增数据库迁移。
- Decision: 保留原始 upstream response ID、attempt index、failure stage 和最终客户端状态，确保计费只结算实际成功流。

## Risks / Trade-offs

- 重放会增加上游请求量和尾延迟 → 限制最大跨账号尝试次数，使用指数退避与抖动。
- 上游错误分类不完整可能误重放 → 仅白名单错误码/语义，已输出内容一律不重放。
- 多实例之间冷却状态不共享 → 先复用现有账号调度状态；若观测仍有同步撞击，再单独评估 Redis/DB 协调。

## Migration Plan

1. 补充网关行为和场景测试。
2. 在本地完成定向 Go 测试与构建。
3. 部署到 `test` 分组可观测灰度，确认 503 暴露下降且无重复计费。
4. 经指标确认后再进入生产分组灰度；保留旧容器以便回滚。
