## Context

当前内容审计默认对普通用户按内容哈希抽样，对有历史命中的用户进入强制全量审查。未被抽中的内容在当次请求结束后不可回溯；已审计日志只保存脱敏摘要，不适合充当离线二次审查原文。

用户已确认使用阿里云 OSS Bucket `sicts`，Region 为 `oss-us-east-1`。当前 Bucket 是私有 ACL，但尚未配置服务端加密、生命周期和访问监控。现有全局 AccessKey 只允许用于创建项目专用 RAM 凭证和 Bucket 策略，不得进入应用运行时。

## Goals / Non-Goals

- Goals:
  - 用有界、可计量的短期证据池支持每日二次审查。
  - 使离线审查结果进入现有高危用户强制全量审查与分级处置链路。
  - 保证云凭证最小权限、证据加密、自动过期、管理员访问可审计。
  - 控制实时热路延迟、OSS 存储量和夜间审查费用。
- Non-Goals:
  - 不全量归档所有用户完整对话。
  - 不将 Redis 或向量数据库作为原始证据主存储。
  - 不因离线模型的单次命中直接封禁用户或惩罚共享上游账号。
  - 不在第一期做语义向量检索或话术聚类。

## Decisions

### Decision 1: 采集新增客户端内容，不重复保存完整上下文

- 网关复用现有内容审计协议规范化器，只提取当次新增的客户端 `user` 内容和可归因的客户端工具输出。
- 不保存平台 system prompt、上游凭证、请求 header 或应用自身注入的指令。
- 每条证据保存内容哈希、原始/存储字节数、截断标记和策略版本。相同用户的相同内容在 TTL 内去重。
- 默认单条规范化明文上限为 64 KiB，单用户每日默认最多 20 条、最多 1 MiB，均可配置且有服务端硬上限。

### Decision 2: 风险加权抽样与实时审计抽样相互独立

- 普通用户采用每日稳定的确定性随机抽样，默认目标是活跃用户和请求的小比例，不得因重试重复采集。
- 新注册、高频调用、多 Key/IP 异常、历史临界分和已有风险事件可提高抽样权重；权重只决定证据采集，不直接触发处置。
- 已进入现有高危监控的用户仍在实时路径 100% 审查，离线证据采集仍受每日上限限制。

### Decision 3: PostgreSQL 保存元数据，OSS 保存应用层加密原文

- 新增 `ContentModerationEvidenceStore` port，阿里云 OSS 适配器使用官方 Go SDK v2，从进程环境/密钥提供器读取项目专用凭证。
- 对象路径为 `risk-evidence/pending/YYYY/MM/DD/<shard>/<evidence-id>.json.zst.enc`；命中人工复核的证据转移到 `risk-evidence/flagged/`。
- 明文先压缩，再使用应用层 AES-256-GCM 信封加密，并同时开启 OSS 服务端加密。加密主密钥与 OSS AccessKey 分离注入。
- PostgreSQL 保存 `object_key`、用户/Key/请求归因、采集原因、字节数、哈希、密钥版本、状态和过期时间，不保存原文。
- `pending/` 原文默认 3 天过期，`flagged/` 默认 30 天过期；应用清理与 OSS Lifecycle 双重执行，数据库保留无原文的审计结果。

### Decision 3A: 加密原文与自动审核副本分离

- OSS 信封内保存截断后的规范化原始新增内容，不在加密前执行会破坏语义的通用脱敏，以便在保留期内还原案件意图。
- 自动审查前仅在内存中生成语义保留型副本：替换密码、Token、Cookie、Authorization、私钥和 URL 敏感查询参数的值，同时保留凭证类型、同一条证据内的引用关系、URL 结构、Hash、UUID、代码和自然语言上下文。
- 审查副本不写入 OSS；原始内容和审查副本均不得进入 PostgreSQL、Redis 或日志。数据库只保存类别、分数、原因码和不含原文的结构化摘要。
- 若证据包含同一个秘密多次，使用仅在该证据内稳定的占位符（例如 `<SECRET:token#1>`）；不得使用可跨证据关联或支持字典攻击的秘密哈希。

### Decision 4: 全局凭证只引导，运行时使用项目专用 RAM AccessKey

- 使用本机钥匙串中的全局凭证创建 RAM 身份 `sub2api-risk-evidence-prod`。
- 应用 RAM Policy 仅允许列出 Bucket `sicts` 的 `risk-evidence/` 前缀，以及对 `sicts/risk-evidence/*` 执行必要的 Put/Get/Delete/分片操作；不授予创建 Bucket、修改 ACL、生命周期、加密、Policy 或 RAM 的权限。
- 新 AccessKey Secret 只在创建响应中出现一次，由引导脚本直接写入 macOS 钥匙串和生产受限密钥文件，不输出到终端、不进入 shell 历史。
- 项目配置只保存 Bucket、Region、Endpoint、Prefix 和密钥引用；不在 Git 跟踪文件中保存任何 AccessKey。

### Decision 5: 每日审查任务使用持久化任务和单实例锁

- 新增审查运行、证据项、风险事件和用户风险画像表，状态迁移可恢复。
- 夜间任务默认每日本地时间 02:00 运行，使用 PostgreSQL advisory lock/现有 leader-election 模式保证单实例。
- 任务按证据 ID 分页，有每日项数、Token 和费用预算；超额项保留到下一批，不无界重试。
- 二次审查不向模型发送用户邮箱、API Key、IP 或上游账号信息，只使用不透明 case ID 和内容证据。
- 存储、解密或审查依赖失败时，只记录可重试错误和心跳，不触发自动处置。

### Decision 6: 离线风险先升级监控，再进入分级处置

- 用户风险画像是数据库真实源，Redis 只缓存强制全量审查标记。
- 首次高置信离线命中将用户升级到 `watch`/`high`，写入有原因码和到期时间的风险事件，并使现有实时审查对其 100% 采样。
- 只有重复高置信命中、明确严重类别或管理员复核确认才能进入现有禁用 Key/用户链路。自动处置不得禁用或惩罚共享上游账号。
- 风险等级具有 TTL，管理员可以复核、降级或解除标记，所有读取原始证据和处置操作必须记录安全审计日志。

## Risks / Trade-offs

- 短期保存原始内容增加隐私和凭证泄漏风险 → 仅保存客户端新增内容、应用层加密、最小权限和短 TTL；自动审核只接收内存生成的语义保留脱敏副本，人工原文访问另设二次授权和审计。
- 风险加权采样可能对某些用户形成偏差 → 保留可再现的抽样原因和基础随机样本，分离“抽中”与“处置”。
- 二次审查模型可能误判 → 首次命中只升级监控，处置需重复证据或人工复核。
- 证据采集会影响热路性能 → 采用有界异步队列、压力下丢弃证据而不阻塞业务，并对丢弃率告警。
- 全局凭证已在会话中出现 → 只用于引导并尽快轮换；生产从不读取该凭证。

## Migration Plan

1. 经用户批准本提案后，使用全局凭证创建项目专用 RAM 身份/Policy/AccessKey，配置 Bucket 加密、访问监控和前缀生命周期，并完成上传/读取/删除探针。
2. 发布数据库表、OSS 存储适配器和管理配置，保持采集与夜间审查关闭。
3. 在 staging 以人工合成内容验证加密、TTL、幂等、断点恢复、密钥权限边界和删除。
4. 生产先以极低基础抽样和“只记录、不升级”模式启用，观察热路延迟、丢弃率、OSS 字节和审查成本。
5. 经人工样本验证后开启高危用户升级；自动禁用保持关闭，直到单独批准。
6. 回滚时先关闭采集/审查开关，保留数据库审计表和 OSS Lifecycle；不恢复已过期原文。

## Phase 1 Decisions

- 第一期复用现有内容审计的 Base URL、模型、API Key 池、重试和分类阈值，任务本身使用独立策略版本、每日条数和 Token 预算；独立审查渠道留作后续兼容扩展。
- `flagged/` 原文保留期采用 30 天服务端硬上限，管理员可配置更短保留期；`pending/` 最长 3 天。
- 费用预算字段默认关闭。现有 Moderations 兼容响应没有可靠 usage/价格来源，在没有可信成本值时不得伪造费用；先以条数和 Token 双预算限制任务规模。
