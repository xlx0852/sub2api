## Context

现有链路是“请求前查快照，请求后原子扣费”。原子扣费只能防止数据竞态，不能防止多个在途请求共同消费同一份可用额度。

## Goals / Non-Goals

- Goals: 防止并发透支、防止无价格免费调用、保持计费幂等、支持失败回滚。
- Non-Goals: 不改变模型单价、分组倍率、媒体按次定价和用量展示口径。

## Decisions

- Decision: 采用 reserve/capture/release 三阶段结算，而不是在后扣 SQL 中简单禁止负余额。后者会在响应已交付时丢失账务。
- Decision: 预留金额使用请求可推导的保守上限；无法推导时使用可配置最低预留额，并受账户并发上限保护。
- Decision: PostgreSQL 作为金额真相源；Redis 只用于低延迟可用额镜像和 TTL 恢复。
- Decision: 本地生成的每请求/每 turn ID 是幂等主键，不信任上游 ID 的唯一性。

## Risks / Trade-offs

- 预留过高会降低低余额用户的并发能力；通过模型上限和最低预留策略调整。
- 进程崩溃可留下未释放预留；通过 TTL 和后台扫描恢复。
- 无价格 fail-close 会改变当前兼容行为；需先审计线上近期零价格模型。

## Migration Plan

1. 增加预留数据结构和幂等 repository API，默认不启用准入拦截。
2. 上线只观测的价格预检和预留金额计算，对比真实费用。
3. 先对管理员测试分组启用，再分批扩大。
4. 开启未定价模型 fail-close，最后移除旧的零费用回退。
